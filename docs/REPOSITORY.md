# Repository guide

This repository follows a production-shaped MVP layout so it can run as a small public pilot on Hugging Face while staying reusable for future RAG systems.

## Main folders

### `packages/rag_core`
Reusable engine and adapters.

- contracts for LLM, embeddings, vector stores, corpus sources
- default implementations for Transformers, multilingual E5, FAISS, and local/HF corpus loading
- retrieval pipeline, prompts, citations, and utilities

### `apps/api`
Thin FastAPI HTTP service.

- `main.py` - app bootstrap and routers
- `settings.py` - environment-driven configuration
- `wiring.py` - creates the embedder, vector store, LLM provider, and pipeline
- `routes/health.py` - health endpoint
- `routes/chat.py` - custom streaming SSE endpoint for the optional Next.js UI
- `routes/openai_compat.py` - OpenAI-compatible `/v1/models` and `/v1/chat/completions` for OpenWebUI

### `apps/web`
Optional Next.js frontend (no longer the default UI).

- `/api/chat` proxy route
- streamed answer rendering
- source inspection panel

### `scripts`
Offline indexing and schema export.

### `data`
Sample corpus; sample index is generated by the build script.

### `docker`
Container startup scripts plus OpenWebUI compose setup (`docker-compose.openwebui.yml`).

## What is modular

You can swap the following without rewriting the whole repository:

1. model provider
2. embedder
3. vector store
4. corpus source
5. prompt/policy layer

Backends can be selected by built-in key (for example `openai`, `e5`, `faiss`) or by custom callable path (`module.path:factory`).

## Artifact strategy

The application repo should stay small. Large artifacts should live in separate Hugging Face dataset/model repositories and be downloaded on boot or mounted through cached Hub downloads.
